Stop and roll back if the private allocation fails, the sidecar binds outside the VPC address or outside the isolated relay range, B fails health within 120 seconds, any non-TURN runtime configuration differs, B owner/reception/endpoint rows change unexpectedly, or an Android ANR/OOM appears. After the one scored C3 call, restore Node B's original TURN configuration before any F test.

This changes a test-only server runtime setting and temporarily restarts Node B; it can interrupt B during the bounded restart window. It is reversible at the container/configuration level. Normal runtime requests may append ordinary server call/audit rows; no database contents are manually edited or rolled back.

## Single private TURN sidecar retry after exec denial (2026-10-31)

The first restart attempt for the private listener exited before opening a socket: exit code `255`, `exec /usr/bin/turnserver: operation not permitted`. Read-only inspection confirmed the pinned image build applies file capability `CAP_NET_BIND_SERVICE=+ep` to `/usr/bin/turnserver`; the failed container ran as UID `1000:1000`, with `no-new-privileges=true`, `cap-drop=ALL`, and no added capability. Sol's review identified the bounding-set interaction as the likely cause: dropping the file capability from the permitted bounding set can make `execve` return `EPERM`. No listener was created, and Node B configuration and database were untouched.

One retry is approved with exactly one container-security change: keep `--cap-drop=ALL` and add `--cap-add=NET_BIND_SERVICE`. Keep the same pinned image digest, UID, `no-new-privileges`, read-only root filesystem, host network, VPC-only bind address, resource limits, secret handling, listener/relay ports, and Node B configuration. Do not add `NET_ADMIN`/`SYS_ADMIN`, use privileged mode, change seccomp/AppArmor/SELinux, or try another launcher/configuration variant. The capability is required by the image's file-capability check even though the listener port is above 1024.

Immediately before the single retry, recheck the existing stop gates (A/B/C health, no active modem/server call, root free space at least 3 GiB, `MemAvailable` at least 1 GiB, ports free). If the process exits, the capability error remains, binding/authentication fails, or any stop gate is crossed, remove only the failed test container/config and stop this sidecar path; do not retry again or touch Node B. On success, verify the VPC-only bind and authenticated allocation before considering the separately recorded Node B TURN-URL change. This retry is only a private-listener smoke test and does not count as C3.

The retry met those gates and passed the authenticated allocation preflight: the process remained running without restarts, TCP/UDP listeners bound only to the VPC address, and the REST-authenticated allocation returned a relay port inside `49300-49399`. Node B remains unchanged. Sanitized measurements are in `c3-b-private-turn-sidecar-retry-20261031.txt`.

## H1 mesh rollback fallback

Sol's source review confirmed that normal UI reorder/selection cannot force the currently offline C gateway healthy, and the UI refuses to remove active B. After the scored call is idle and H1's incoming setting is restored, the planned fallback is a separate test-only instrumentation invocation of the existing production methods `HostNodes.activate(C)` followed by `HostNodes.remove(B)`. It will run only after force-stopping Madoka so no `MainActivity` or `NodeMonitor` can race the switch; it will not launch a UI, alter SIM state, or edit SQL. Require `activate(C)` to return C and verify it is locally active before calling remove. After `remove(B)`, verify by read-only SQL that H1's B device is revoked and its endpoint withdrawn, while H2 remains the only eligible client on B; verify the local node list contains only C. `remove()` catches revoke errors and still clears local state, so a mismatch is a hard stop: preserve evidence and leave the residual server state for Kiri; never repair it with SQL. If C activation fails, do not remove B. This fallback changes H1's local active session and revokes the newly added B pairing; the saved same-AVD backup is retained until the before/after identities and server revocation are verified. Restoring B would require a new normal join code and is not automatic.
