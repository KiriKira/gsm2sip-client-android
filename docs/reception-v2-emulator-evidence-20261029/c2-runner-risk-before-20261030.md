# C2 runner and real-call retest — pre-change record

Recorded before starting the two H1/H2 `HostJointInstrumentation` runners on 2026-10-30 UTC.

The test will archive, not reuse, the stale runner mailbox files on H1 and create a pairing-reuse fixture for H2 from the already validated H1 fixture. It will not read or export pairing tokens, change a pairing, modify SQL, install a product APK, change system permissions, or use root/Magisk. Both runners call the production visible-listening entry point and temporarily enable incoming reception; their `finally` path disables it. After the test, the normal Madoka settings UI will be used to restore the required incoming state, with server settings verified read-only.

The case will originate only real GSM calls from the Homura emulator and allow actual FCM delivery. The instrumentation mailbox will issue the planned answer/reject actions. A mailbox `OK` is only evidence that a synchronous UI action returned; Android Telecom state and SoulGem call/participant records determine the call outcome. Calls may create ordinary test call rows and may ring until the normal ring timeout. If either runner fails readiness, a call remains active, or the incoming switch cannot be restored, stop that case, preserve logs, and clear only the reserved emulator call through the normal emulator command. Rollback consists of stopping the instrumentation, ending any test call, restoring incoming reception in the app UI, and archiving the current mailbox; no database or full app-data restore is planned.

H1/H2 clocks will be sampled against the test host before timing actions. If offset/error bounds or runner result timestamps cannot establish the planned approximate 0.5-second action separation, report the timing assertion as unverified rather than infer it from sequential shell sleeps.

The first harness precheck used the number of `SET_RINGING` lines in `dumpsys telecom`; H1's bounded history had reached its entry cap, so the count did not show the fresh ring and the script canceled the call before issuing any action. A subsequent focused log read confirmed both hosts had fresh `Incoming call ringing`, CallActionActivity, and Telecom RINGING events. No answer/reject was issued, so this is a discarded harness attempt, not a product failure or scored C2 trial. The next attempt will gate on fresh `HostJointInstrumentation` status replies with `phase=INCOMING_RINGING` and matching call IDs, corroborated by live app/Telecom logs; it will not use Telecom event-history counts.
