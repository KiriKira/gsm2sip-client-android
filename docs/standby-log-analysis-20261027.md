日期：2026-10-27（北京时间）。状态：根据用户导出的三段诊断形成的建议，尚未实施本文新增改动。

本次源码审查基线：Madoka `731209f8c28b2b39b57baa44540170c55047f536`；SoulGem `60eeaedfc92230fa22da9a2182d794b414aa3dbc`。Madoka 主线已含 `095ca8c` / PR #32 的故障恢复修复。本文接续 [唤醒锁修复计划](idle-wakelock-fix-plan-20261027.md) 和 [实施记录](idle-wakelock-implementation-20261027.md)，用实际诊断重新确定优先级。

## 1. 已确认的主因

**`rtc-compat-idle` 正在按现有策略持续持锁。上一轮客户端修复改善了工作锁和生命周期，但没有解决正常在线待机的主耗电来源。** 这次不需要继续猜测到底是哪把锁。

三段分别按 `sampled_at - segment_started_at` 计算统计区间；锁占比是持锁时长/区间时长，不是耗电占比，也不是 CPU 利用率。

| 版本/分段 | 区间 | RTC 物理锁累计 | 占区间 | 兼容待机所有者 | 同步锁 |
| --- | --- | --- | --- | --- | --- |
| `v0.4.4` | 6h04m14.511s | 6h04m13.812s | 99.997% | 旧格式没有原因统计 | 55.617s |
| `0.4.2-build-57-9aefbef` | 3h29m34.362s | 3h28m50.181s | 99.649% | 3h28m09.515s | 30.593s |
| `0.4.2-build-58-095ca8c` | 1h24m58.564s | 1h24m57.413s | 99.977% | 1h24m57.373s | 4.668s |

不能因为显示 `0.4.2-build-*` 就断言降级；应使用提交哈希判断代码。也不能把跨进程、不同版本的累计锁直接当成同一个连续区间。

最新 build-58 的证据：

- `rtc-signaling.held_ms = 5,097,413`，`longest_ms = 5,097,372`，采样时仍持有；几乎整段连续持锁。
- `rtc-compat-idle = 5,097,373ms`，而 `rtc-control-work = 30,374ms`，后者只占统计区间约 0.596%。所有者时间可重叠，**不能相加或相减推算可节约的电量**。
- `rtc_poll_idle = 181`、`rtc_poll_succeeded = 181`，没有记录 live/failed 事件；这段主要是在正常空闲监听，不支持“通话没结束导致一直快轮询”的解释。
- `release_failed_idle_experiment = true` 只在连续失败至少三次且没有通话时释放待机锁。这里 RTC 轮询没有失败，所以开关不会触发。HTTP 其他路径少量失败不等于引擎连续轮询失败。
- WSS 连接累计 `5,079,021ms`，约占区间 99.62%；持锁并非主要发生在长时间没有连接的阶段。

**验收目标应从“总请求减少”改为“健康空闲时兼容锁占比显著下降”。只缩短补查和同步锁，不会消除本例的约 85 分钟连续持锁。** 累计值有短暂增长本身正常；本例的问题是增长速度几乎等于墙钟时间。

## 2. FCM、网络变化和三节点的准确解释

### FCM 已有实际到达证据，但尚无休眠接听能力

build-57 的 `push_by_node` 记录三个匿名节点的接收；`actual_priority = original_priority = 1` 对应 FCM HIGH。该段 `push-handoff` 仅持锁 259ms，兼容待机却仍有约 3h28m。

这证明当时高优先级推送确实进入应用；不能据此断言每次推送都能到、该提示必定是实际来电、或手机当时处于 Doze。build-58 的 `last_fcm_received_at = 0` 仅表示这个进程分段没有记录到 FCM，不能认定 FCM 已失效。

源码中 `pushReady` 主要决定空闲轮询间隔；`updateContinuousLease()` 正常空闲分支仍选择 `COMPAT_IDLE`。所以“FCM 有效时依然持续持锁”符合当前实现。

### 网络稳定性还需要分清原因

build-58 有 `network_changed = 10`、WSS 打开 10 次/关闭 9 次，导出时 `stable_network = false`。网络事件计数发生在合并通知之前，不能直接称为十次真实切网；也不能据一个最终布尔值判断整段都不稳定。

当前 `NetworkEnvironment` 的签名仍包含其他网络身份、validated/metered 状态；改变后会触发 `HostBackgroundService.onNetworkEnvironmentChanged()`，关闭并重建 WSS。`clearSocket()` 又调用 `NetworkEnvironment.failed()` 重置稳定窗口。这里存在减少非必要重连的机会，但**日志没有时间线，不能证明 VPN、某个能力位或某次主动重连就是这十次变化的原因**。

### 三节点维护是次要负担

build-58 共记录 **897 次应用 HTTP 请求**，其中：

| 类别 | 次数 | 判断 |
| --- | --- | --- |
| RTC control 写入，三个节点合计 | 384 | 每次发送 28 字节，与当前 v1 资格声明格式一致；需增加明确类别后逐接口确认 |
| 活跃节点 RTC control 读取 | 181 | 与成功空闲轮询次数吻合，平均约每 28.2s 一次 |
| `node_probe` 的 capabilities + metadata 读取 | 207 | 备用节点仍持续探测；可减少重复请求 |
| 其余请求 | 125 | 包含同步、其他维护等，不应全部算作来电轮询 |

其中活跃节点资格写入 169 次，平均约每 30.2s 一次。持续续租是现协议的主要固定维护开销。各行 `elapsed_ns` 是含网络等待的耗时，不能相加当作 CPU 时间；应用字节不包括全部 TCP/TLS/WSS 流量。

## 3. 修改建议 A：先把当前运行模式讲清楚（客户端 P0）

修改位置：`calls/StandbyPowerPolicy.kt`、`calls/RtcCallEngine.kt`、`data/StandbyDiagnostics.kt`、`MainActivity.kt` 待机设置。

1. 统一暴露当前模式：`compat-idle`、`ringing`、`live-call`、`failed-backoff`、`offline`、`disabled`；同时记录进入时间、最近切换原因、当前阻止休眠的原因。不能仅展示一个“省电已开启”。
2. 设置中明确显示：“当前为兼容接听，正常在线时持续持锁”；故障退避开关旁说明：“仅连续连接失败时生效，健康联网时不降低待机持锁”。
3. 导出加入模式驻留时间、进入/退出次数、连续失败计数，以及 `sleep_blocker = legacy_online_lease` 等固定枚举。按引擎实例分段、匿名节点归因；多所有者重叠不求和为物理锁时间。用户能直接看到是哪一条接听策略阻止休眠。
4. 把 `/rtc/control/capability` 和 `/rtc/control/calls` 从现有 `rtc_control` 聚合中分开，区分引擎与备用节点维护的请求原因。保留旧字段或注明诊断 schema 版本。

完成条件：像 build-58 这样“开了故障省电但正常在线”的状态，页面和导出能直接解释持锁原因，无需再上传几十项请求计数猜测。此项改善解释性，本身不降低主锁时间。

## 4. 修改建议 B：收窄网络事件造成的主动重连（客户端 P1）

修改位置：`network/NetworkEnvironment.kt`、`StableNetworkWindow`、`background/HostBackgroundService.kt` 的 `onNetworkEnvironmentChanged()` / `clearSocket()`、`mesh/NodeMonitor.environmentChanged()`。

按以下规则拆开“实际路径”“可用性”“费用属性”，不要一个指纹变化就做完整恢复：

| 事件 | 应执行的动作 |
| --- | --- |
| 默认 Network 切换、默认接口/路由/DNS 实质变化、VPN 接入/退出 | 合并后立即补查；需要迁移旧连接时重建 WSS；清除对应路径缓存 |
| 同一默认网络从未验证恢复为已验证 | 立即重试失败任务；已有健康 WSS 不因这一位变化强制关闭 |
| metered 改变 | 更新调度策略；不直接重建 WSS，不清空有效元数据 |
| 无关非默认网络上线/下线 | 不直接清空当前路径的稳定窗口或重建 WSS |
| VPN 的实际底层路径改变 | 能识别关联时立即补查；不能可靠识别时先做一次受限业务检查，以真实失败决定重连，不把所有旁路网络变化都当作隧道断开 |
| 实际 WSS 断开、HTTP 连续失败 | 重置连接健康并恢复；保留失败退避和系统恢复入口 |
| 用户主动切节点/关闭监听 | 按原生命周期关闭旧连接；这不是网络健康失败 |

实施细节：

- 为 WSS 关闭增加固定原因枚举，区分远端关闭、I/O 失败、路径迁移、令牌更新、用户停止。主动关闭不自动记成网络失败。
- 路径稳定窗口与服务连接健康分开计时；路径真的改变应重置路径窗口，不能用“忽略全部失败”制造稳定假象。
- 保留 1.5s 合并；以合并后的最终状态与上次已处理状态比较，避免先失去/又恢复同一路径仍触发多轮重连。
- 增加最多 32 条脱敏事件环形缓冲：单调时间、事件类型、是否重连、是否重置稳定窗口。不存 SSID、IP、DNS 值、路由或 token，不每次写文件。
- 不添加信号强度主动轮询或新定位权限；不要根据 RSSI 瞬时抖动恢复连接。

完成条件：单纯 metered/无关网络变化不导致 WSS 重连；默认路径或 VPN 真切换仍触发即时恢复。已有系统回调、短交接锁和失败恢复逻辑必须保留。预计减少重连和强制探测，**不会独立释放 `compat-idle`**。

## 5. 修改建议 C：降低三节点重复维护（客户端 P1）

修改位置：`mesh/NodeMonitor.kt`、`data/RtcCapabilityRefresh.kt`、`calls/RtcCallEngine.kt`、`background/HostBackgroundPolicy.kt`。

1. 保留同会话、同路径的 RTC 成功证据复用；独立记录控制读取 RTT，避免把能力续租/认证刷新/多次业务读取累计耗时当成单次路径 RTT。客户端成功响应不能代替 Homura 在线状态。
2. 健康探测按“活跃节点、可接替节点、长期不可达节点”安排到期时间；节点恢复、实际业务失败和用户检查可提前触发。低优先级且稳定的备用节点建议以 300s 为起始调度值，失败按节点退避；活跃业务故障仍立即做有限故障切换，不等慢周期。
3. 活跃引擎和 NodeMonitor 使用同一成功续租截止时间，按节点合并在途资格请求。保留当前成功去重，诊断先证明是否还有重复发送，再调整周期；不能仅靠两个独立的 30s timer 保证不重叠。
4. **当前协议下，仍承诺即时接听的备用节点不能直接停掉资格续租，也不能把它拉长到 300s**。90s 候选资格与慢速健康探测是两回事。后台停掉备用资格若会降低可达性，必须明确成为用户选择的接收范围，不能偷偷改变默认能力。
5. 网络稳定后沿用现有元数据 600s、健康探测最长 300s 的策略；不要继续仅增大参数掩盖“稳定窗口反复重置”。WSS 双向心跳先保留现状，已有单侧心跳试验不与本次变化捆绑发布。

完成条件：诊断能按节点说明减少的是 capabilities、网关读取还是重复资格；当前节点失败仍及时恢复新业务。不要将这些请求下降写成“持续唤醒锁已修复”。

## 6. 修改建议 D：真正降低健康待机主锁的方案（P0 架构工作，服务端仅留计划）

**推荐主路径：有效休眠接听资格 + 实际推送唤醒 + 有限工作锁。** 即使此前已收到 FCM，也必须先解决服务端候选规则，才能让客户端停止正常空闲续锁。

### D1. SoulGem 的最小必要改动

涉及 `internal/httpapi/rtc_control.go`、`push.go`、能力声明与数据库迁移；本轮不实现。

- 显式协商休眠接听能力；设备声明接听意愿，并获得服务端确认的有期限订阅。绑定账户、有效会话、设备和当前推送 endpoint 代际。
- 入站候选允许“90s 在线设备”或“有效休眠订阅设备”。关闭接听、配对撤销、会话/endpoint 失效时撤销订阅；服务器重启后保留有效状态。
- 保持现有 25s 来电窗口、20s 活跃控制租约和多端获胜规则；唤醒后仍由 HTTPS 校验真实通话状态。
- 来电推送优先、有界并发，修复坏 endpoint 导致串行队头阻塞；持久化发送意图/认领，窗口内有限重试。中继接受与设备实际拉取到事件分别记录。
- 先兼容 Kyubey v1 内容空提示；迟到提示只补查，过期来电不响铃。完整 mesh 和媒体路径改造不是本项目的前置。

### D2. Madoka 在 D1 可用后切换策略

涉及 `StandbyPowerPolicy`、`RtcCallEngine.updateContinuousLease()`、`NodeMonitor.maintainOwned()`、`HostBackgroundService`、`PushRegistration` / `PushWake`。

- 只有服务器明确确认订阅、当前 endpoint 有实际到达证据且无通话时，才进入 `push-idle`。日志里收到过 HIGH 是证据的一部分，不是永久可靠性证明，也不冒充深睡来电试呼。
- 在进入休眠的同一个状态转换中，取消该节点空闲 RTC 轮询、30s 在线资格维护和连续兼容锁。短信兜底、WSS、备用节点维护要同时服从该模式，避免另一个循环立即把手机拉回持续工作。
- 推送、用户操作、系统实际提供的恢复机会触发短锁补查；响铃/建媒体转交通话所有者；终态或空结果后立即归还。
- 任一仍要求兼容即时接听的节点都可能阻止整机深睡；不能只给活跃节点开休眠，却让备用节点维持持续锁，再宣称已省电。
- 订阅拒绝、明确推送失败或用户选择恢复兼容时，在应用可执行时恢复接听。静默丢失的 FCM 不能在深睡客户端被立即发现；保留可选择的兼容策略，不承诺无条件零漏接。

完成条件：无通话、无提示、订阅有效的静默窗口中，`rtc-compat-idle` 不再增长；仅实际工作留下短锁。代码和 CI 不能替代之后的深睡来电验收。

## 7. 无 FCM 的具体取舍

当前没有系统推送时，默认“即时接听”继续依赖兼容监听。建议 B/C 能减少 CPU、请求和无线网络活动，但不能承诺消除本例的主锁。

两条可选的后续路径应单独设计：

1. **被动 WSS 接听试验**：在目标设备确认深睡网络包能及时让应用执行，并由服务端解决连接关联的候选资格。仅保留 socket 或前台服务不保证能唤醒；即使网络能唤醒，旧 90s 资格仍可能先过期。两项依赖均解决后才考虑默认启用。
2. **用户明确选择延迟接收**：允许周期恢复时才刷新资格/补查，释放空闲连续锁；界面必须说明可能错过 25s 窗口，只能稍后看到记录。它适合明确接受延迟的用户，不能作为“无 FCM 即时接听节电”的验收结果。

不能通过“每次 poll 后直接 release”、一律 5 分钟轮询、或频繁精确闹钟来宣称兼得深睡和即时接听。当前 `RtcFailureRecovery` 已为连续失败场景安排有退避的非精确空闲闹钟；它不应扩张为健康待机的常态保活。

计算：区间 `T = sampled_at - segment_started_at`；物理锁占比 `held_ms / T × 100%`；平均请求间隔 `T / 次数`。系统可能调整墙钟，后续导出宜同时记录单调时钟的进程采样区间；这些占比按本次提供的字段计算。匿名 node 编号只在其进程分段内有效，不跨分段推断服务器身份。

源码入口（路径相对 `app/src/main/java/com/callagent/host/`）：
