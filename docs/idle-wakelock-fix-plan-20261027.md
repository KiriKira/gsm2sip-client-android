# Madoka 持续待机唤醒锁修复计划

日期：2026-10-27。状态：第一批客户端改动已实现并提交 PR #30，见 [实施记录](idle-wakelock-implementation-20261027.md)；服务端休眠资格与客户端推送休眠尚待实施，尚无真机节电结论。

审查基线：Madoka `729c74a27d875ebad86f9e86aba8db743879dd25`（含 PR #27、#28）；SoulGem `60eeaedfc92230fa22da9a2182d794b414aa3dbc`。手机安装包的具体提交尚未确认，不能直接把仓库版本等同于截图版本。

本计划接续 [上一轮计划](standby-optimization-plan-20261026.md) 和 [实施记录](standby-optimization-implementation-20261026.md)。上一轮减少了请求、断网持锁和无效节点维护，**没有消除正常在线空闲时的持续信令锁**。本轮以持锁和实际功耗为验收对象。

## 1. 证据与优先级

用户提供的同日统计：

| 指标 | Madoka | 微信 |
| --- | --- | --- |
| 后台时长 | 5 小时 9 分钟 | 5 小时 12 分钟 |
| 唤醒锁 | 3 小时 48 分钟 | 1 分钟 |
| CPU | 16 分钟 | 1 分钟 |
| Wi-Fi 包数 | 60,642 | 86,630 |
| 移动网络包数 | 434 | 210 |
| 系统耗电归因 | 3.5% | 0.6% |

Madoka 持锁时长约为后台时长的 74%，应优先调查。唤醒次数为 0 不代表 CPU 可以休眠；一直持锁也可能不产生该页面统计的频繁唤醒。数据包较少仍然可能更耗电，包数不等于无线电活跃时间。系统百分比不直接换算 mAh；两款应用的工作负载、系统待遇也不同。

源码已确认以下机制，尚未通过手机锁 tag 完成归因：

1. `calls/RtcSignalingWakeLease.kt` 的 `host:rtc-signaling` 每次申请 60s，20s 后允许续租；`RtcCallEngine.connect()` 和正常 `poll()` 均调用续租。成功轮询后不释放，健康在线监听可以连续持锁。
2. `RtcCallEngine` 的 `pushReady` 仅改变轮询周期，不改变持锁。30s 的推送模式轮询仍短于 60s 锁租期，FCM 可用也不能因此进入深睡。
3. `NodeMonitor.maintain()` 独立刷新多个节点的资格；只让引擎休眠，其他维护路径仍可能继续产生工作。
4. `HostBackgroundService.runSync()` 的 `host-sync` 使用 60s 上限和 finally 释放，但锁范围还包含推送登记等工作；需要分阶段耗时才能确认是否也是主要来源。
5. SoulGem 在 `internal/httpapi/rtc_control.go` 冻结入站候选时要求最近 90s 的 capability。停止续租后，服务器可能根本不给休眠设备生成来电事件。已有 WSS、普通定时线程、网络回调都不能普遍保证 Android 深睡中的及时执行。

**处理顺序：锁归因 → 明确锁所有权 → 无 FCM 优化 → 推送休眠。** 不再把改大轮询间隔作为主要的持锁修复。

## 2. 交付范围

- **客户端近期修复**：锁生命周期、重复任务、失败待机、无 FCM 下的 CPU/请求优化，可独立发布。
- **小范围客户端 + SoulGem 协议改造**：让已验证推送的设备真正休眠。无需等待 mesh；这是新增的独立工作包，不再全部推迟到远期 mesh。
- **无 FCM 的空闲释锁试验**：在目标手机上验证被动 WSS 到达和资格续租；通过门槛才考虑扩大启用。保持即时接听的兼容模式明确报告剩余持锁，不宣称问题已完全解决。
- 本轮不做节点复制、路径选优、TURN 迁移或 Homura 架构重写。优先兼容现有 Homura、Kyubey v1；若联调证明有缺口，再单独列出必要变更。

## 3. R0：用现有诊断完成归因

修改入口：`data/StandbyDiagnostics.kt`、`calls/RtcSignalingWakeLease.kt`、`background/HostBackgroundService.kt` 和现有设置诊断页。

1. 先利用现有 JSON 导出记录版本、区间、`rtc-signaling` / `host-sync` 累计及最长持有时间、节点数、FCM 登记与实际接收状态。对比同一统计区间；不能拿整日系统计数与新进程计数相减。
2. 补充持锁原因：兼容待机、入站补查、响铃、活跃通话、同步；记录各模式驻留时间和模式切换原因。物理锁时间与原因时间分开，重叠原因不相加冒充总持锁。
3. 补充同步阶段耗时、RTC 成功/失败次数、空闲快轮询次数、capability 次数。检查通话结束后是否残留 `media` / 非终态 `delivered`，导致长期 750ms 轮询。
4. 保留内存聚合、低频落盘；不逐轮询写文件，不导出号码、正文、地址或凭据。进程异常尾段标记不完整。

完成条件：能回答这台手机 3h48 中应用已记录的主要锁与原因；若应用统计解释不了，使用一次同区间系统 batterystats/bugreport 检查库或系统归因。归因数据不阻塞已确认的代码修复，但发布说明必须区分确认项与推断项。

## 4. R1：把“引擎活着就持锁”改为明确所有权

修改入口：`RtcCallEngine`、`RtcSignalingWakeLease`、`CallRuntime`、推送入口、`HostBackgroundService`、`NodeMonitor`。新增一个共享的待机策略与锁所有者协调器，避免每个模块独自判断是否应休眠。

| 状态 | 锁与任务策略 | 退出条件 |
| --- | --- | --- |
| 停止接听 / 会话失效 | 取消该会话空闲任务，释放其待机锁 | 显式重新启用且会话有效 |
| 无默认网络且无活跃通话 | 无空闲持锁，无网络请求 | 实际网络恢复事件 |
| 兼容在线监听 | 独立的 `compat-idle` 原因拥有必要保活；不再由每次 poll 隐式续租 | 停止、失效、断网、进入已允许的休眠模式 |
| 有限补查 / 重连 | 工作开始获取短锁，完成即释放；所有权覆盖异步交接 | 完成、失败、取消或工作预算到期 |
| 响铃 / 建立 / 活跃通话 | 通话拥有锁，随有效状态续期 | 终态或原有失联控制规则触发 |
| 已允许的推送休眠 | 无空闲信令锁、RTC 空查和 30s 资格续租 | 推送、用户操作或系统实际提供的恢复机会 |

实施约束：

- 每个所有者持有独立 token，释放自己的 token；一个 sync 的 finally 不得释放仍在接听或建媒体的锁。会话代际改变后，迟到任务不能重新拿锁或恢复 enabled。
- 短工作初始预算 15s；现有较长同步可保留 60s 硬上限，但完成即释放。预算要传到 HTTP 超时/取消和循环中，锁超时不能掩盖后台任务仍无限运行。活跃通话用原租约独立续期，不套短任务截止时间。
- 推送回调交给 worker/服务之前建立有界所有权；服务成功接管后释放回调所有权；启动被系统拒绝、普通优先级、异常、空结果均有释放与降级路径。
- 通话终态及时清除媒体和活动标记；只要仍有真实呼出/响铃/活跃通话，关闭“接收来电”不能误释放通话资源。
- `NodeMonitor`、RTC 引擎、后台同步共用同一会话的资格状态；保留最新主线对真实路径变化和不可达节点的修复。

R1 本身不保证兼容在线监听持锁下降，它使后续释锁有正确的生命周期边界；交付时不得称其已解决 74% 持锁。

## 5. R2：FCM 不可用也要交付的优化

### 5.1 默认路径：减少可证实的无效工作

1. WSS 提示、网络恢复、轮询、推送合并为一次在途补查；执行期间的新提示只产生最多一次尾随补查。按节点/会话合并，避免一个节点吞掉另一个节点的来电提示。
2. 同一节点一次 RTC 成功请求更新健康证据；资格到期时与现有请求同一工作批次处理，继续利用成功续租去重。不为“检查网络”额外发送探针，不让慢元数据或历史查询阻塞来电。
3. 无待处理短信/历史、缓存未过期时跳过相应工作。`host-sync` 在必要同步和通知结束后释放；推送登记/低优先级维护分离预算，不能延长整段同步持锁。
4. 正常稳定 Wi-Fi/VPN 沿用现有降频策略。只对实际默认路径、VPN 路由变化或业务失败触发恢复，合并切网事件；不新增信号强度主动轮询、定位权限或因 RSSI 抖动反复重连。
5. 先保留兼容来电 3s/8s 的兜底语义；根据计数定位并消除重复请求和残留 750ms 快轮询。更慢参数单独验收，不与锁改造捆绑。

### 5.2 失败期间释锁

没有活跃通话、所有可用节点均失败并完成一轮有限故障切换后，进入“暂不可接听”状态：请求结束释放工作锁，退避期间不续租无效待机锁。

恢复由实际网络回调、用户打开、已有允许的后台任务或设备自然唤醒触发；设备保持清醒时可继续退避定时器。**同一网络内服务器恢复不会必然产生网络回调，普通 timer/WorkManager 也不保证秒级恢复。** 在目标机验证并明确这项恢复延迟后才默认启用；要求持续即时探测的兼容选项保留。不得用每几秒精确闹钟或重启服务补回已释放的锁。

### 5.3 稳定网络下无锁 WSS：独立试验，不暗中降级

实现显式的“无推送省电试验”策略：无通话时释放连续待机锁，收到实际 WSS/网络/前台事件后短锁补查。应用说明锁屏来电可能延迟，默认兼容模式不自动切入。

试验必须检查两件不同的事：① 目标机深睡时数据包能否让应用及时执行；② 超过 90s 后服务端是否仍将它列为候选。短时间锁屏成功不代表整夜成功；WSS `onOpen` 也不等于睡眠可达。即使某台手机被动收包有效，服务端候选资格问题仍需独立解决。

若实测需要服务端支持连接绑定的候选资格，再开一个受限协议扩展：只认可对应认证连接、接听偏好及有效会话，断连/撤销失效；不能仅延长全体设备的 90s TTL。没有实测证据时不将此扩展列入默认发布，也不宣称它能跨越 Doze/OEM 限制。

**无 FCM 验收单独报告 CPU、锁、耗电及来电结果。** 如果默认兼容路径只是 CPU 降低、持续锁仍占大头，应如实保留这一未解决项；不可用有 FCM 的收益抵扣。

## 6. R3：推送可用时真正休眠的最小协议改造

### 6.1 SoulGem：接听意愿与“90s 在线”分离

新增显式能力协商（例如 `push_idle_reception_v1`，名称在实现时固定），旧客户端/旧服务器沿用现有行为。不要把普通 `capability(true)` 自动解释成长期订阅。

- 新建设备级休眠接听订阅：设备/所属账户、会话代际、enabled、push endpoint 代际、到期时间。服务端时间权威；建议初始上限 24h、可运行时提前续期，且不超过授权会话有效期。后台任务可能延期，临近过期的状态只在应用实际获调度时更新；不声称到期时一定能自动唤醒降级。
- 入站冻结候选接受“现有在线资格”或“有效休眠订阅”。两条路径都检查 active 设备、有效会话、接听意愿；休眠路径还检查当前有效 endpoint。创建来电、冻结候选及可重试的推送意图要有持久化一致性。
- 关闭接听、退出/撤销配对、endpoint 失效或换代使相应订阅失效。离线关闭先在本机阻止响铃，恢复后补撤销，服务端到期兜底；不虚构离线立即撤销成功。
- 客户端唤醒后仍从认证 HTTPS 拉取真实状态，使用原候选和获胜者规则；不能仅凭推送允许接听。保持 25s 来电窗口和活跃通话 20s 控制租约，禁止为了省电放宽通话授权失效规则。
- 服务器重启保留订阅与待发意图；数据库迁移向后兼容。睡眠订阅不是在线状态，也不是永久接听承诺。

### 6.2 推送调度：消除会吃掉来电窗口的队头阻塞

现有 `pushPending()` 最多取 100 条串行发送、每条最多 10s。把休眠作为主接听路径前必须修复：来电优先、有限并发、持久化 claim/租约、按设备合并、在有效窗口内有限重试；一个坏 endpoint 不能阻塞其他来电。服务端区分“中继接受”和“设备拉取到来电”，不把前者当送达。

第一阶段可继续使用 Kyubey v1 的 `kind/device_id` 内容空提示，手机拉取时丢弃过期/已终态来电，不因旧提示响铃；保留 v1 需要的短信补查。已入 FCM 队列的 60s TTL 不能在此撤回，可能产生迟到空唤醒。若数据证明它明显影响待机，再独立加入可传递剩余 TTL 的协议；不把完整 wake v2/mesh 作为本轮前置。

### 6.3 Madoka：登记成功不是休眠资格

- 进入推送休眠必须满足：用户开启接听、服务端支持并确认当前订阅、当前 endpoint 有真实来电到达证据、没有活跃通话。用一次用户可见的真实试呼验证深睡接收；不周期发高优先级静默探测来维持“健康”。
- 证据绑定节点、会话、endpoint 代际；实际 FCM priority、拉取成功、响铃延迟分别记录。注册 `kind=check` 的验证结果不能作为真实投递证明，长时间没有业务也不自动判失败。
- 休眠时暂停该节点 RTC 空查/在线资格维护；推送支持完整覆盖的情况下，关闭用于兜底的持续 WSS 和常规短周期同步，使用已有系统允许的低频补偿。旧节点或无推送节点按自己的兼容策略继续工作；只要有节点要求兼容持锁，整体设备仍可能不能深睡，UI 和诊断要如实说明。
- 推送到达后短锁拉取，真实响铃转交通话所有者；空结果、过期、别处已接听立即结束。终态后重新满足条件再回休眠。
- 收到明确 endpoint 失效、服务端拒绝订阅、推送降级或实际来电失败证据时，在应用可执行时退回兼容模式。**静默丢失的 FCM 无法在睡着的客户端立即被发现；一次试呼成功也不保证以后全部成功。** 保留用户选择兼容模式和清晰的未接来电记录，不承诺不存在的即时自动兜底。

| --- | --- | --- |
| A：归因与锁所有权 | R0/R1、终态与异步交接修复 | 关闭/换节点/结束通话后无遗留所有者，通话中不误释放 |
| B：无 FCM 待机 | R2 的任务合并、缩短工作锁、失败模式；无锁试验独立开关 | 默认路径无新增漏接；真实无 FCM 同条件 CPU/耗电改善可复核；失败释锁恢复边界清楚 |

客户端 B 不等待 C/D 或远期 mesh；C/D 是降低健康在线持续持锁的主要路径。实施时按依赖完成代码，推送 PR 交 CI；不在本地生成 APK。计划不指定版本号，也不自动合并或发布。

### 必要自动化

复用现有测试，只补真实风险：工作完成/异常/取消释锁，推送到服务交接，通话结束与关闭监听竞争，旧会话迟到回调，休眠不被 NodeMonitor 重新续租；服务端增加休眠超过 90s 的真实入站候选、撤销/到期、一个坏 endpoint 不挡另一个来电的回归。避免为每个参数排列、getter 或不可能状态另建测试矩阵。

文档阶段不运行构建或测试。实施阶段由 PR CI 执行对应仓库现有检查和少量新增回归，CI 不能证明真机深睡可达。

### 最小真机对照

先用用户实际手机、同一个服务器、相同 sing-box/VPN 设置，版本基线与候选版各跑一晚至少 6h。分别测真实无 FCM、验证过的 FCM 两条路径；WSS 不通但 HTTPS 可用做短时功能回归即可。切 Wi-Fi/移动网络、开关 VPN、服务器短时不可达各验证一次恢复，不展开全机型全组合压力矩阵。

- 每条接收策略先做至少 10 次随机时刻真实呼入，覆盖锁屏超过 90s、长时间静置及通话结束后再次呼入，记录漏接和到响铃延迟。推送休眠及无锁试验必须实际进入 Doze；保持 USB 连接可能影响结果。任何新增漏接都阻止该策略默认启用；10 次成功不等于生产零漏接保证。
- 安静待机与通话窗口分开记录。推送休眠中 `rtc-signaling` 的 **空闲持锁目标为 0**，有限同步/真实来电的短锁单列；若仍出现小时级持锁，视为失败。
- 记录系统/应用同窗口的锁、CPU、请求数、WSS 重连、来电时延、可用的 mAh/h 或电量变化。无 FCM 默认路径与自身基线比，微信仅作参照；不预设节电百分比。
- 一轮对照只用于筛查明显问题；差异小或环境变化大再重复。请求下降而功耗没有明显改善，标记部分完成并继续定位，不把发布叙述写成“已解决耗电”。

## 8. 回退与完成定义

客户端锁策略、无 FCM 失败释锁/无锁试验、推送休眠分别受控。回退休眠时，先恢复兼容资格和接收，再撤订阅/清理旧任务；不会因先停一条路径而产生新的接听空窗。服务端只在确认协商支持的客户端启用新候选规则，旧接口继续可用。

完成报告必须分别写清：主要锁来源是否得到设备证据支持；无 FCM 默认模式实际减少了什么、还剩多少持锁；推送休眠是否让空闲锁归零；真机呼入和功耗测量结果。未通过真机验收的模式保留试验标识，不用 CI 成功代替电量结论。
