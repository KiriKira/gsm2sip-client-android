| [FCM 消息有效期][F2] | TTL 控制排队时长；`ttl=0` 表示不能立即送达即丢弃；发送成功不等于手机已收到 | TTL 绑定事件截止时间，不默认套用 0 秒；记录提交、接收和响铃三个不同阶段 |

**对初版的四项纠正：**

1. 撤回“已知 call 提示只查来电”的直接改法。服务端 `internal/httpapi/push.go` 在同轮有来电变更时用 `kind=call`，成功后同时推进 `pushed_event_cursor` 和 `pushed_call_cursor`。一个提示可能覆盖两种待同步数据，必须先改协议再精确分流，详见 A4。
2. 将 `PushRegistration.isReady()` 解释为登记状态。Kyubey 的 `check` 是 `validate_only=true`，不实际投递；它更不能证明客户端已被唤醒。[K1][K2]
3. 新增推送有效期、优先级和任务生命周期为释放唤醒锁之前的必要工作。Kyubey 当前所有实际消息固定 `HIGH`、`ttl=60s`；本项目呼入窗口只有 25 秒，迟到提示会带来无效唤醒。[K1]
4. 初版 120 秒兜底、5 分钟元数据、45 秒 Ping、100 秒 Pong、30 秒短锁等数字均无上述成熟项目的直接背书。它们只保留为实验变量，不能当作推荐生产配置；实施第一批时保持现有周期。

Linphone 与 Signal 支撑的是架构和生命周期做法，不构成 Madoka 可以无条件释放待机锁的证明。Signal 的消息获取路径也不等同于完整的来电状态机。

## 1. 结论与范围

最优先处理两件事：减少待机时重复的 HTTPS 请求，以及让具备可靠推送接收条件的手机在空闲时释放 CPU 唤醒锁。前者可以分批落地；后者必须修改服务端来电候选规则，不能仅在客户端删锁或延长轮询。

本文关注熄屏、无通话、无用户操作时的后台接收。通话中的媒体与控制时效继续单独保障。所有新增时间参数均为首轮实验建议值，不是已验证的最佳值；最终以接收可靠性和真机测量决定。

本分支已开始实施，具体范围、默认行为、开关与验证结果见同目录 `background-standby-power-progress.md`。本文后续章节仍保留完整目标设计，不能据此认为所有阶段已经完成。

### 请求量的数量级

在请求耗时很短、持续运行、无事件额外触发的假设下：

- RTC 来电列表：30 秒周期约 120 次/小时，8 秒约 450 次/小时，3 秒约 1,200 次/小时；能力上报另计。
- 短信：30 秒一轮、每轮 4 次请求时约 480 次/小时。
- 多节点：30 秒一轮、每节点 4 次请求时约 480 次/节点/小时；失败复查和跨节点短信状态查询另计。
- WSS：服务端约 180 次、客户端约 144 次 Ping/小时，Pong 另计。

这些是用于定位优先级的估算，不是实测请求数，也不能换算成 CPU 唤醒次数或耗电百分比。固定延迟调度、请求耗时、系统休眠与触发合并都会改变实际值。

## 3. 必须保留的约束

1. **90 秒来电资格。** 服务端 `internal/httpapi/rtc_control.go` 创建呼入时，仅选取最近 90 秒成功上报 RTC 能力、允许接听、配对和会话仍有效的设备；候选列表在创建来电时冻结。休眠后再上报不能自动补进已经创建的来电。
2. **25 秒振铃窗口。** 当前呼入创建后约 25 秒到期。FCM 已登记且 WSS 在线时的 30 秒轮询，本来就无法保证在推送和 WSS 提示同时丢失时及时接到每一通来电。不能把低频轮询描述成完整的实时来电保障。
3. **无 GMS 路线。** 不能假定 WSS 加前台服务必然能唤醒深度休眠的 CPU，也不能用 WorkManager 的周期任务承诺秒级来电接收。
4. **会话和节点隔离。** 缓存、ACK、任务合并和回调必须按配对会话与节点隔离；切换后旧任务不能污染新节点的状态。
5. **持久化顺序。** 先提交 SQLite 数据，再发送事件 ACK；失败时继续重试。通知去重、历史基线同步、分页及 resync 行为必须保留。
6. **停止语义。** 用户关闭接听、停止后台同步、解绑或系统强行停止后，不得用新调度绕过现有选择与 Android 限制。
7. **网络判定。** 系统缺少 `NET_CAPABILITY_VALIDATED` 不一定表示配置的内网/VPN 节点不可访问；明确无网络与“公网验证失败”需要区别处理。

## 4. 第一批：减少重复工作，保持现有接收周期

### A1. 合并节点能力查询

修改位置：`data/ApiClient.kt`、`mesh/NodeMonitor.kt`、`push/PushRegistration.kt`。

实施步骤：

1. 新增统一能力返回对象，至少包含 `rtcCallControl`、`push`、`extensions`；一次 `/capabilities` 响应完成解析。
2. `NodeMonitor.probe()` 一轮只调用一次能力 API，用结果决定 RTC 续租及能力展示，去掉第二次请求。
3. 第一版只复用同一轮结果，避免新增跨轮缓存失效问题；后续再引入按节点缓存，建议初始 TTL 为 10 分钟。
4. 如启用跨轮缓存，另用实际业务请求结果判断节点健康，不能以缓存命中作为“节点刚刚可达”的证据；协议不支持错误、节点地址变化、重新配对时使缓存失效。

验收：支持 RTC 的节点，一次探测的 `/capabilities` 请求数从 2 降到 1；旧服务端和不支持 RTC 的节点行为保持正确。

### A2. 短信事件同步与元数据刷新分开

修改位置：`data/HostSyncEngine.kt`、`background/HostBackgroundService.kt`、`data/ClientDatabase.kt`。

建议接口：`syncEvents(deadline)`、`refreshMetadata(deadline, force)`；名称可按实现调整。

实施步骤：

1. 事件增量同步只负责 `/events`、必要的历史补拉、通知持久化与 ACK，不以网关/SIM 元数据刷新成功作为每轮前置条件。
2. 第一次配对、节点切换、数据库缺少元数据时强制加载网关/SIM。已有有效元数据时，后台建议每 5 分钟刷新一次；打开相关页面或开始依赖映射信息的操作时按需刷新。
3. 对协议已支持的元数据变化事件立即刷新；若事件流没有覆盖某种变化，则保留 TTL 刷新，不假定所有变化已有通知。
4. 网关和 SIM 内容未变时避免重复数据库写入；UI 将缓存状态标为具有时间戳的快照，操作授权仍由服务端核验。

验收：元数据缓存有效、已有事件游标、没有新消息时，普通短信同步仅请求事件接口，不每轮查询网关与 SIM；首次同步、历史分页、SIM 变更和节点切换均能正确恢复。

### A3. 成功 ACK 去重，保留失败重试

修改位置：`data/HostSyncEngine.kt`、`data/ClientDatabase.kt`、`data/ApiClient.kt`。

实施步骤：

1. 持久化 `lastSuccessfullyAckedCursor`，按节点和配对会话隔离。
2. 本地已提交游标与最近成功 ACK 的游标相同时跳过；不同则发送 `/events/ack`，成功后才更新本地确认记录。
3. 游标按不透明字符串处理，不以字典序比较大小。失败时不更新记录，后续即使没有新事件也继续尝试 ACK。
4. 重新配对或数据库重置清除记录。并发同步串行化确认记录更新，避免旧请求覆盖新确认状态。
5. 服务端 `internal/httpapi/client_receipts.go` 在重复 ACK 时会更新 `confirmed_at`。落地前审查该字段的全部读取方，确认没有把它当作设备在线心跳或必要的保留租约；如有，先拆分这些语义，再去重。

验收：连续空事件轮次不重复确认相同游标；ACK 失败后下一轮仍发送；进程重启不丢失待确认进度；不同节点之间不共享 ACK 状态。

### A4. 先明确提示覆盖范围，再分流与合并请求

修改位置：`push/PushWake.kt`、`background/HostBackgroundService.kt`、`calls/RtcCallEngine.kt`。

实施步骤：

1. 第一版保持旧 `v=1` 提示的双路补查，先合并重复任务；`call` 立即优先查询来电，短信补查不阻塞它。原因是服务端一个 call 提示同时消费了两类推送游标。
2. 新版本提示协议建议显式提供 `scopes=[sms,call]` 和不含业务内容的 `wake_id`，服务端只推进本次提示确实覆盖的游标；中继明确透传已允许的字段。客户端在协商成功后才精准分流。旧客户端/中继保留现有双路语义。WSS 当前只有通用 `sync_required`，同样不能凭提示猜测数据类型。
3. 将短信的 `syncQueued` 扩展为“正在运行 + 尚未处理的请求”状态。同步过程中收到新提示时，结束后最多追加一次补查，避免单纯丢弃提示而等到下个周期。
4. 合并以节点/会话为边界；来电提示立即查询，不使用秒级防抖等待。短信提示可在已有任务期间合并。
5. 网络切换、WSS 恢复和 FCM 同时到达时，共享同一轮同步；节点切换时使旧轮次失效。

验收：同时收到 FCM/WSS 不产生并行重复同步；事件发生在已发出查询之后，仍通过补查获取；call 提示不等待短信网络任务完成；同一轮同时产生短信和来电时两者均被获取；新旧版本混用不吞掉某一类提示。

### A5. 建立推送任务所有权，参考 Signal 的有限队列

证据：[S1][S2]。修改位置：`push/MadokaMessagingService.kt`、`push/PushWake.kt`、后台/通话服务入口；建议新增 `PushFetchCoordinator`。

1. 推送入口先核验类型、版本和设备配对，将收到时间、实际优先级、原始优先级传给协调器，不能只把 `data` 传下去。
2. 按 `(node, sessionGeneration)` 保存运行任务和待补查 scopes：每种拉取最多一个执行中、一个合并后的待执行任务；来电查询不排在慢速短信任务之后。新增提示只扩大补查范围，不不断开新线程。
3. 服务/系统任务持有本轮工作所有权，等认证请求、SQLite 提交、通知处理全部结束再释放。WakeLock 仅保证 CPU 运行，不能替代服务/系统任务的进程生命周期保障。
4. 实际高优先级推送且满足平台条件时使用匹配用途的服务；启动失败必须记录异常并走允许的恢复路径。短信可用立即调度的 expedited work 补充处理，普通后台同步用普通 work；两者都不承诺来电的秒级时效。[F1][A1]
5. 对 `onDeletedMessages()` 增加幂等补查：已有游标继续拉取、按服务端 resync 恢复快照；遵守用户停止状态，不自动打开已关闭的接听。
6. 旧节点回调、超时、进程重建、重复推送和认证失效都必须使任务完成或转移，避免留下无主锁/无主服务。过程指标包括入队、开始、持久化、通知、释放及失败原因。

验收：FCM 回调已返回、应用进程此前不存在时仍可完成接收；突发 100 个相同提示不会产生 100 个 HTTP 轮次；同步过程中新增数据能通过一次补查获取；服务启动被拒时有明确诊断结果。

## 5. 第二批：后台调度与心跳

本批的分钟级周期与心跳参数属于 Madoka 实验设计，未从 Linphone/Signal 源码取得可直接移植的参数。前置条件是第一批请求统计和接收可靠性基线齐备；默认维持现有参数，逐项灰度验证。新协议推送模式中取消不必要常驻连接，优先级高于在兼容模式里寻找一个所谓“通用最佳心跳”。

### B1. 短信兜底按状态选择周期

修改位置：`background/HostBackgroundService.kt`、`background/HostBackgroundPolicy.kt`。把固定周期改成一次性调度，每轮结束计算下一次时间。

| 条件 | 首轮建议 | 恢复/触发规则 |
| --- | --- | --- |
| 空闲、WSS 已成功打开且最近健康 | 120 秒短信兜底 | 收到提示立即同步；首轮验收后再评估 300 秒 |
| WSS 不健康，网络可用 | 保留 30 秒短信兜底 | 不因“FCM 已登记”就直接延长到数分钟 |
| 明确无网络，无进行中通话 | 暂停常规网络请求 | 网络恢复时合并触发一次；重新读取实际网络状态以处理回调遗漏 |
| 网络存在但服务器连续失败 | 30、60、120、240、300 秒上限，±20% 抖动 | 新网络、有效推送或成功请求触发恢复；401/会话撤销走独立认证处理 |
| 正在使用页面或有待处理业务 | 保留业务所需及时刷新 | 前台与后台共用请求结果，避免两套任务重复请求 |

WSS 健康状态须以成功打开和失联检测为依据，不能只判断 `socket != null`，因为连接建立中也存在 socket 对象。

风险与验收：WSS 提示丢失时，短信补收延迟上限会相应增加。记录这种情况下的延迟，确认 120 秒上限可接受；短信通知失败重试应保留独立调度，不能因修改兜底常量而无意放慢通知投递。

### B2. 多节点健康、能力续租、历史状态各用自己的截止时间

修改位置：`mesh/NodeMonitor.kt`、`mesh/CrossNodeStatus.kt`、`calls/RtcCallEngine.kt`。

实施步骤：

1. 活跃节点优先利用最近一次 RTC/短信成功请求判断连接情况；只在需要网关状态或故障确认时追加完整探测。
2. 当前协议下，RTC 续租统一由一个按节点管理的调度器负责，初始建议每 30 秒一次；活跃节点与备用节点都避免重复续租。续租所有权迁移必须保证不会出现两个模块都认为对方负责的空档。
3. 健康备用节点的完整健康探测初始改成每 120 秒；失败节点按 30→60→120→300 秒退避。即使完整探测放慢，当前协议的 90 秒资格所需续租仍须单独保持。
4. 活跃节点实际请求失败、默认网络变化、非活跃节点收到推送时立即重评；保留必要的二次失败确认。
5. 跨节点短信状态仅在有未终结发送任务时查询；终态停止。按任务记录下一次检查时间，初始建议 30 秒，连续失败逐步退避至 5 分钟。
6. 通话中继续遵守现有禁止随意切节点的约束，不能将空闲切换策略套用到活跃媒体。

验收：空闲多节点请求量随节点数的增长低于基线；每个需接听节点的 RTC 能力仍不超时；主节点故障后的切换时间不劣于同条件基线。若仅慢速探测导致切换变慢，应由业务请求失败触发快速评估。

### B3. WebSocket 使用一套心跳

修改位置：客户端 `background/HostBackgroundService.kt`；服务端 `internal/httpapi/wake_websocket.go`。

实施步骤：

1. 首轮评估关闭客户端主动 Ping，保留 OkHttp 对服务端 Ping 的自动 Pong，以及服务端当前 20 秒 Ping/45 秒 Pong 超时。
2. 补充客户端的失联探测设计：去掉主动 Ping 后，半开连接可能仍被客户端认为在线。利用兜底 HTTPS 失败、连接回调及服务端断开行为修复，测试下行黑洞/上行黑洞；若无法保持足够快的故障发现，不能直接采用该方案。
3. 单套心跳稳定后，再根据连接存活与黑洞恢复数据选择候选间隔。初版提出的服务端 Ping 45 秒、Pong 等待 100 秒仅作为未验证实验组合留档，不设为生产目标。需同时核对负载均衡、反向代理、NAT/VPN 的最短空闲超时。
4. 若更长心跳导致重连率上升或漏接，回退原间隔；用每小时总报文及重连成本衡量收益。

验收：Ping/Pong 往返减少，连接重建次数不增加；Wi-Fi、移动网络、VPN 和网络切换都能及时发现失联。不能把“减少一套 Ping”直接等同于功耗下降某个百分比。

## 6. 第三批：推送待机真正释放 CPU

这是预期收益最大的结构性改造，也是风险最高的一批。第一、二批不移除现有信令唤醒锁。

### C0. 先修复服务端—Kyubey—手机的推送契约

证据：当前中继 `src/fcm.js`、`src/relay.js` [K1][K2]；FCM 有效期/优先级文档 [F1][F2]。本节是释放锁的前置任务，不能只修改 Android。

**当前缺口：** `check` 仅让 FCM 校验发送请求，不送到手机；真实推送统一 HIGH/60 秒；发送字段只允许 `sms|call|check` 和 `device_id`，没有来电截止时间；Madoka 不记录实际优先级，也没有 `onDeletedMessages()` 处理。

建议协议新增下面的信息，字段名为设计草案，尚未实现：

| 字段/状态 | 归属 | 用途与约束 |
| --- | --- | --- |
| `wake_id`、`scopes` | 服务端生成、中继受限透传 | 合并重复唤醒并明确覆盖的数据类型；不包含号码或正文 |
| `expires_at` / 剩余投递预算 | 服务端生成，中继限制可接受范围 | 真实来电 TTL 不超过有效接听剩余预算；每次重试重新计算，到期不再发送实时来电提示 |
| `purpose` | 服务端事件分类 | 区分真实新来电/入站短信通知，与发送回执、状态更新、历史补拉；后者不反复使用高优先级 |
| `received_at` / 认证唤醒确认 | 客户端经现有认证 API 上报 | 证明到达具体设备；不以 Kyubey 200 或 FCM message ID 代替手机确认 |
| `endpoint_generation` | 配对与端点管理 | 换 token/端点后旧确认不能继续被算作新端点健康 |

具体时序建议：

1. 为一通呼入保留一个服务端权威截止时间 `D`。所有候选设备、提示重试、客户端拉取与振铃共用此截止时间；重试不得重新延长电话的寿命。
2. 在发送时计算 `remaining = D - server_now`。若没有足够时间完成认证拉取和用户可见振铃则不再发送实时来电提示，转为结束后的记录同步；该余量从实测延迟选择，不能固定宣称需要 2 秒或 5 秒。
3. 中继根据剩余预算设置有限 TTL，而不是固定 60 秒。`ttl=0` 会牺牲暂时离线后的补投，不作为默认省电开关。短信是持久数据，不能套用来电 TTL；同时有两种 scopes 时要确保来电过期不会丢掉短信补查需求。[F2]
4. 重复唤醒可以合并，但不能用一个全局 collapse key 让另一节点/另一通来电或短信覆盖掉仍需处理的信息。新协议下明确合并范围；旧提示继续用幂等拉取兜底。
5. 服务端调用中继成功只记为 `submitted`；手机经认证拉取/确认才记为 `received`，Telecom/通知实际展示另记为 `presented`。收到迟到提示时必须重新核验终态，不制造新的振铃。
6. 高优先级只用于有对应及时用户可见结果的事件。检测实际降级和通知权限/渠道被关闭的情况；不要用周期高优先级“探活”代替常驻轮询，避免制造另一种持续唤醒。[F1][S2]

推送通路验证建议在用户可见的设置流程中进行，或利用实际业务推送的认证回执建立证据；`check` 继续可用于令牌/配置校验，但 UI 不应称它为“熄屏接收测试通过”。

### C1. 服务端区分在线设备与可推送唤醒设备

修改范围：服务端 RTC 能力/来电候选查询、推送登记与撤销、会话撤销；客户端能力协商。

建议的协议语义（尚未存在，需版本协商）：

- `online`：沿用现有短期在线续租，适用于旧客户端和无推送客户端。
- `push_reachable`：用户明确允许接听、配对及会话有效、设备声明支持新协议、推送端点有效，允许无近期在线心跳时成为候选。
- 来电候选依然只包含授权设备；推送成功提交给中继不能代替客户端的接收确认。服务端保留带截止时间的待接来电，恢复认证后再交付，与 RFC 8599 的待投递请求模式相对应。[R1]
- 推送唤醒后客户端先读取并核验来电，服务器记录到达确认时间；超时、拒绝、其他设备接听仍按现有状态机结束。
- 关闭接听、解绑、会话撤销、端点永久失败时立即撤销资格。临时推送失败需有可观测状态与恢复策略。
- 推送资格需要有界有效期及维护机制；具体 TTL 与系统允许的后台维护频率一并设计，不能换成另一个几十秒续租任务，也不能无限信任历史登记。

兼容要求：新服务端显式公布该扩展；旧服务端或未协商成功时，客户端保持原模式。不能仅把 SQL 的 90 秒改成几天而继续认为设备在线。

### C2. 客户端状态机

修改位置：`calls/RtcCallEngine.kt`、`calls/RtcSignalingWakeLease.kt`、`calls/HostCallService.kt`、`push/PushWake.kt`、`push/PushRegistrationPolicy.kt`。

| 状态 | CPU 锁 | 网络行为 |
| --- | --- | --- |
| 兼容接收模式 | 保留当前有超时的续租机制 | 保留当前 RTC 接收与短期能力续租 |
| 新协议推送待机，无通话 | 不持续持信令锁 | 停止秒级 RTC 轮询；维护任务允许系统批处理 |
| 收到真实来电提示 | 取得有超时的短锁 | 立即认证查询来电，核验后提交 Telecom/通知；合并重复提示 |
| 振铃/建立连接/通话 | 保持相应阶段的可靠运行保障 | 沿用通话控制时效与媒体授权检查，单独管理锁生命周期 |
| 通话终止并完成必要清理 | 释放相关锁 | 返回推送待机或兼容接收模式 |
| 用户关闭接听/解绑 | 释放锁并撤销资格 | 不自动恢复接听 |

短锁预算应不超过该阶段剩余业务截止时间与网络总预算，并在完成后立即释放；不把初版的固定 30 秒视为成熟项目推荐值。跨异步回调必须有明确所有者，失败、超时、服务销毁和节点替换都能释放。不能只在 FCM 回调返回前持锁，否则异步网络任务可能失去保护。振铃/通话阶段需要自己的锁所有权，不能因一次拉取结束而误释放整个活跃通话的保障。

进入推送待机需要：服务器支持新协议、端点登记成功、真实到达链路已验证、允许接听且当前无通话。单凭 `PushRegistration.isReady()` 不足以判定。

多节点需分别判断：如果任一仍承担接听职责的节点不支持新协议，不能全局关闭其能力续租。UI 展示每节点模式与原因，整体可为混合模式。服务端先兼容部署、客户端确认协商成功、最后启用休眠；回退兼容模式时先成功恢复在线能力续租，再撤销推送专用资格，避免切换瞬间出现空档。[L1]

FCM 高优先级消息、后台服务启动和通知展示受 Android/厂商规则影响，必须真机验证。降低或延迟的推送不能被承诺一定在 25 秒窗口内送达；异常要可观测，支持用户选择兼容接收模式。设备已沉睡时也不能假定客户端能主动察觉每一次未到达的推送并立即回退。

### C3. 同时消除其他持续唤醒来源

仅释放 RTC 锁而继续保持短周期 WSS 流量，收益可能受限。新协议推送待机阶段进一步评估关闭或显著减少自有 WSS 保活；前台使用、通话和兼容模式仍可保留 WSS。

短信兜底、节点维护、推送资格维护应合并为系统允许的批处理任务。WorkManager 可用于非实时维护，但不能用于保证来电秒级触达。前台服务是否继续常驻需要结合实际服务类型与启动限制另行实现，不能把“停止前台服务”作为单独可靠的省电措施。

### C4. 本次发现的新平台方向：AndroidConfigV2 仍为预览

截至本次查阅，Firebase 官方已公开 [AndroidConfigV2 迁移文档][F3]，页面明确标为 Preview。它区分用户可见的 `RemoteNotification` 和非紧急的 `BackgroundSync`，并引入新的客户端回调。

这可以作为后续 Kyubey 协议演进的观察项，不加入当前生产改造的必要依赖。本次检查的 Signal 和 Kyubey 文件仍使用旧式消息处理/配置，不能声称它们已经迁移。Madoka 必须额外验证 SDK 与旧客户端兼容、通知回调和 Telecom 的衔接、鉴权后展示规则以及数据最小化，再决定是否试验。不要仅因文档写着新 API 就把 `android.priority` 直接替换掉。

## 8. 验收方案

### 8.1 先加可量化观测

按单调时钟记录或聚合以下指标，避免每次轮询输出大量磁盘日志：

- 按接口和触发原因统计请求次数、失败次数、耗时及字节数；原因至少包括周期、FCM、WSS、网络恢复、节点探测、前台操作。
- 各 WakeLock 的累计持有时间和获取次数，重点关注 `host:rtc-signaling` 与 `com.callagent.host:host-sync`。
- WSS 连接次数、断开原因、稳定存活时长、Ping/Pong 数量。
- 节点切换次数和耗时，成功 RTC 续租间隔。
- 来电创建→推送发送→客户端收到→认证拉取→响铃的各阶段耗时；跨设备时间戳需校时，避免错误相减。
- 短信事件提交→客户端持久化→通知展示耗时，以及重复通知数。
- 推送实际/原始优先级、FGS 启动被拒原因、expired wake 数、`onDeletedMessages()` 次数；按端点代际与节点统计 submitted/received/presented，避免把登记成功算成真实触达。

统计中不记录令牌、推送端点、号码或短信正文。

### 8.2 自动化回归（实施对应改动时执行）

- 复用并扩展现有 `HostBackgroundPolicyTest`、`PushPolicyTest`、`NodeMonitorIsolationTest`、`RtcSignalingWakeLeaseTest` 和数据库持久化测试。
- 验证新调度的各状态与边界：连续失败、恢复、用户停止、旧回调、节点切换、同时收到多个提示。
- 使用受控 HTTP 响应计数验证请求减少，不以“函数被调用次数”代替实际 HTTP 请求数。
- 服务端验证：休眠设备在新模式下可成为候选；旧客户端仍遵守原规则；撤销设备无候选资格；晚到推送不能复活已结束来电。
- ACK 测试包含数据库提交成功/失败、ACK 响应丢失、进程重启、跨节点游标相同但语义不同等情况。
- 同轮短信+来电只产生一个旧式 call 提示时两类数据均补齐；新协议 scopes 混用正确。验证 60 秒迟到提示、过期 TTL、重复 wake、其他设备已接听、端点换代以及 FCM 被降级。

### 8.3 真机对照

基线版与优化版使用相同设备、系统、账号、节点数和网络配置。拔电、熄屏，关闭无关高耗电应用；每组至少测 8 小时并重复 3 次，记录信号强度、温度、电池容量/电量与系统策略。分别测有 GMS 和实际需要支持的无 GMS 设备。

| 场景 | 需要确认 |
| --- | --- |
| 单节点、Wi-Fi、整夜无业务 | WakeLock 时间、CPU suspend、请求数、整夜耗电 |
| 单节点、移动网络/弱信号 | 无线电活跃时间、重试和重连是否放大 |
| 多节点空闲、主节点断开与恢复 | 请求是否随节点数过快增加；来电资格和切换时效 |
| 长时间熄屏后随机来电/短信 | 及时到达、无重复、拒接/接听可用 |
| Doze、电池豁免开/关、目标厂商后台限制 | 分别记录实际行为，不把模拟器熄屏通过当作深度休眠通过 |
| Wi-Fi/移动网络切换、VPN、单向黑洞 | 失联检测、节点恢复与调用去重 |
| FCM 延迟/丢弃、WSS 提示丢弃 | 各路径的真实保障边界及补收延迟 |
| 用户停止、解绑、重启、端点变更 | 尊重停止状态、授权和资格正确恢复/撤销 |

功耗对照与密集来电压力测试分开进行，避免测试流量掩盖待机功耗。可采集 `dumpsys batterystats`、`dumpsys power`、`dumpsys deviceidle`、Perfetto 和可用的电量计数据；采集命令及充电状态必须记录，持续 USB/ADB 连接可能干扰休眠结果。

建议首轮可靠性门槛：各关键接收场景至少 30 次随机触发来电，测试样本内无漏接且均在有效振铃窗口内出现；同时报告 P50/P95/最大延迟。30 次零失败不证明生产环境零漏接，需保留长周期观测。

省电收益以实际 mAh/小时、可用的能量指标和系统归因交叉判断；电量百分比仅作辅助。第一批验证重复请求确实消失；第三批验证空闲信令锁持有时间接近零且 CPU 确实进入休眠。未测量前不承诺固定百分比改善。

## 9. 当前证据的局限

现有 `docs/webrtc-screenoff-validation-20261019.md` 包含约 79 秒熄屏后呼入、约 81 秒熄屏通话及模拟器验证，明确尚未验收真机 HAL、厂商电池策略和强制深度 Doze。它能证明对应条件下的功能行为，不能证明当前版本整夜待机功耗或新推送休眠方案可靠。

当前 `MainActivity` 的页面定时任务在 `onPause()` 移除；`RtcAudioSession` 的媒体轮询在建立媒体后运行。它们不是本次代码审查中已经确认的空闲待机首要问题。除非后续测量发现生命周期泄漏，否则优先处理上述持续信令、重复同步与保活请求。
