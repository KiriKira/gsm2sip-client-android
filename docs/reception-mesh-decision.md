# 接收协议与远期mesh：范围整合决定

状态：2026-10-27设计修订，未实现。输入是[Claude第一轮评审](https://github.com/KiriKira/gsm2sip-client-android/pull/37#issuecomment-6447204378)、三端最新main及[原mesh计划固定版本](https://github.com/KiriKira/gsm2sip-server/blob/d354ea20b7d6b820dccb15693b47916d482d2934/docs/decentralized-mesh-plan-20261026.md)。当前执行路线以[精简PLAN](reception-v2-PLAN.md)为准。

## 1. 决定

**统一共用协议，分开交付复杂能力；废止原两份计划的完整前置任务链，保留mesh文档作为架构参考。** 先R1解决手机省电与电话/短信解耦；有出口问题先考虑R2a受信Kyubey备用地址，仍不能解决再做R2b单跳推送代发。R3业务单入口代理和更完整去中心化复制按实际需求另立项目，不占R1发布门槛。

不直接放弃多节点协作的目标，因为“一个出口不通时另一个帮忙”成本可控且有实际收益。但单跳代发不等于真正去中心化mesh：它不复制历史、不接管故障源节点，也不能让手机只连A就读取B的全部业务。

## 2. Claude评审逐项处理

| 意见 | 处理 |
| --- | --- |
| 6张以上表、13个接口、10阶段太重 | 采纳。首版一张偏好表、一项GET/PUT配置资源；复用端点、call/participant/event表与cursor；按四仓库工作包推进 |
| 当前没有事件清理/cursor过期，不该先造快照系统 | 采纳。`event_feed.go`实际读取server_events，已有短信feed直接保留；删除30天过期、410、bootstrap/snapshot和cursor迁移 |
| no_subscribers可能阻断其他节点 | 第二轮更正：现有GATEWAY_UNAVAILABLE已按REJECTED处理且继续B/C，本来就没有该分叉缺陷。新错误码只区分没人订阅/网关不可用，须加入同样分类，UNKNOWN仍走既有终态处理 |
| 5秒时钟校验与跨端绝对时间过重 | 采纳目标，使用Homura单调剩余预算+服务端首次deadline，不要求设备时钟对齐；同call重试不延长 |
| WSS等500ms再push增加时延 | 采纳。可用通道同时发，客户端去重；省电不靠拖延真实来电 |
| 四阶段receipt可以先只做日志 | 采纳。保留本地诊断，不新增receipt表/API；provider受理与真实展示仍严格区分 |
| Kyubey未能核实 | 已核实`28213b59`源码；固定60秒TTL与字段过滤确实存在，wire2改造保留为硬依赖 |
| 基线过时 | 已合入Madoka main `6e8aee8`，核对SoulGem `494c420`与Homura `31f65a7` |
| enabled+可用push/最近在线即可入候选 | 部分采纳。持久enabled保留；瞬时failures>0不能取消资格，否则又会为证明健康增加轮询。投递路由健康单独判断 |

另一个源码确认的必要修改：`rtcCandidateSQL`还用于outgoing授权。若只改incoming开关，主动拨号会被误禁；R1明确拆开，不能靠临时重新启用incoming绕过。

## 3. 能共用什么，为什么不能全部一起做

| 能力 | 实现难度及新增负担 | 决定 |
| --- | --- | --- |
| 持久接收意图、call/SMS分流、真实TTL、去重 | 中等；主要修改已有表/接口/Android生命周期，四仓库部署需要协调 | R1，两个计划共用唯一实现 |
| 同密钥受信Kyubey备用地址 | 较低；固定origin别名、原密封路径、已有发送重试；不能解决共享基础设施故障 | R2a，优先于peer转发 |
| 一跳A→B→Kyubey代发 | 中等；增加peer认证、有限目的地址和预算转发，复用R1 sender/wake格式 | R2b，仅在受信备用地址不能解决时交付 |
| 手机一个入口读取/控制其他节点 | 高；现有owner/device/session与mapping_revision均节点作用域，媒体鉴权精确绑定session，不能把A bearer直接当B凭证 | R3有明确需求再实施；不包装成一个HTTP代理就完成 |
| 历史与配置持久复制，源节点永久丢盘后仍可用 | 高；需要身份映射、来源顺序、去重投影、删除/撤销一致性、补洞与恢复；改变数据权威和恢复方式 | 当前不排期，保留独立设计参考 |
| 完整控制路由/owner fencing | 高；要跨节点授权并保持Homura执行唯一性；分区或超时不能自行争抢控制权 | 当前不排期；活跃通话仍固定原节点 |
| 全局媒体路径评分/TURN目录 | 中高；HTTP RTT不能代替媒体质量，必须调整候选凭据/ICE与两端音频诊断 | 先保留ICE+现有TURN，出现实际媒体路由问题再做 |
| 自动成员发现、大规模gossip、活跃通话透明迁移 | 很高；超出当前三节点主要故障范围 | 从当前路线移除，不列为“稍后顺手完成” |

整合能省掉重复的接收协议、push TTL、关闭语义和来源标识设计；不能省掉跨库一致性和跨节点鉴权。这些不是多加几个字段就自然获得的能力。即便把所有工作写在同一张计划里，实际难度仍是R1加上一个分布式系统项目。

不列天数估算：目前没有实现吞吐数据；上表按新增持久状态、信任边界和必须修改的现有模块判断。R1的工作量主要在Android生命周期与跨端兼容，R2a主要在已受信中继路径配置，R2b主要在服务器出站代理；两者可明确隔离故障面。

## 4. 与原S0–S6/F1–F3映射

| 原计划 | 现在处理 |
| --- | --- |
| S0本地可靠性 | 有界并发、领域独立水位/退避和deadline并入R1；完整outbox/多API领取按实际部署需要再加 |
| S1成员+代发 | 优先用R2a备用地址，必要时才缩成R2b静态可信peer的一跳同步代发；先不做通用成员变更、邀请传播和远程持久任务接管 |
| S2事件复制 | 冻结。现有Homura扇出与手机去重继续；没有数据复制需求就不建log/inbox/offset/snapshot体系 |
| S3控制路由 | 冻结。R3只在出现入口隔离需求后先做有界代理，仍有唯一业务来源，不假称已支持owner迁移 |
| S4及F1/F2推送休眠 | 被R1替代。取消短睡眠租约、周期自测和全部节点证明健康才休眠的要求；不再以完整mesh作为前置 |
| S5媒体路径 | 留作独立可选优化，现阶段依靠原ICE/TURN |
| S6活跃迁移/大拓扑 | 从当前承诺移除 |
| F3客户端单入口 | 依赖真实R3路由后再做；R2代发不删除手机访问独立origin的必要连接 |

原文中“休眠必须有近期触达证据/订阅短期续期”、多阶段receipt及全套复制测试均不再是本次实现要求。原文关于跨节点鉴权、Homura副作用唯一性、节点cursor不可混用等事实仍作为后续设计约束保留。

## 5. 第二轮评审与R2能力边界

[第二轮评论](https://github.com/KiriKira/gsm2sip-client-android/pull/37#issuecomment-6448183099)的处理：

- 拒接问题属实；用户已明确选择“拒接结束整通来电（所有设备停止）”。R1新增协商后的decline_all操作，由Homura将全局拒接与winner提交到同一个持久裁决，结果经现有terminal队列传播所有分叉。仅修改单节点reject不足以实现该目标。关闭监听仍只影响本机；旧协议下明确显示能力限制。无需新建四阶段推送回执系统。
- 采用TTL/Urgency标准HTTP头，删除正文ttl_ms；Kyubey读取并映射到FCM，旧头缺省兼容。HTTPS地址校验不代表实现全部UnifiedPush/WebPush协议。
- 采用按endpoint+kind隔离限流，SMS突发不占call桶；不宣称消除了FCM项目级限流。
- 采用进程内按设备/generation/call的已受理revision缓存与失败退避；不让未推进的批水位使已成功来电每秒重发。缓存丢失可重复投递，持久事件仍是恢复依据。
- 恢复提交后立即唤起dispatcher，每秒扫描只补漏；不新增消息总线或完整outbox。
- 明确sms_enabled=false同时停服务端SMS push/WSS hint和手机自动同步，保留显式操作/历史；重开按原cursor补齐。
- 取消额外中继握手API。旧Kyubey确实能将新正文降为v1，但**不能对旧手机一律输出wire2**：当前MadokaMessagingService显式拒绝v不是null/1的消息。服务端仍按接收配置version区分设备，新手机接受旧格式有界补查。
- Kyubey `seal.js` 的AAD固定为kyubey-endpoint-v1，没有host字段；同密钥/相同格式/兼容FCM项目的可信实例确可作为别名。先修WAF/域名配置或使用固定受信备用地址，再考虑R2b。不能把任意推送端点的hostname换掉，也不能把密钥泄露给普通peer。


A的Kyubey出口不通、A本身仍可服务手机且A↔B正常：B可以代发，手机被唤醒后向原A查状态。A宕机：单纯代发不能让手机读到A的call，也不能保证此前未交给B的数据存在。所有节点共用的Kyubey/FCM失败、手机无GMS/Doze限制：换SoulGem出口不解决。

R2b使用固定受信peer，不设唯一常在线中央节点，每个节点可以对称成为代发者；这是有限对等协作。R2b仍保留业务源节点作为该业务权威，因此不是完整去中心化业务集群。

未来真正要求“源节点宕机，其他节点继续同一业务”时，需要明确选择事实复制范围与控制权转移，届时重启独立mesh项目。不要现在为该承诺引入未使用的六七套状态表。

## 6. 测试范围决定

R1只验日常Wi-Fi/VPN、移动、电话关闭+短信、真实三节点分叉、重复/迟到提示、一个慢endpoint、实际升级回退和两段待机。保留关闭/accept、短信幂等、旧端点回调等高后果的小型自动用例。

R2a实施时只验主地址故障/受信备用成功及禁止未知origin；R2b实施时再验出口失效转发、全部出口失败和未授权peer拒绝。没有实现S2/S3就不跑乱序复制、分区选主、备份克隆、百节点/百慢端点测试；也不要求每种网络下30次电话或固定三轮8小时。R1发现回归时只扩展直接相关用例。
